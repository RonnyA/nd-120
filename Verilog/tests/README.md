# Test suite — what runs, what doesn't, and why

## The two commands

```
cd Verilog
make test        # every self-checking unit testbench, FAIL-FAST
make test-full   # adds the heavy system gates (latch-vs-FF golden trace,
                 # runSim golden console, Tang vtest boot+deposit)
```

**Fail-fast matters:** the first failure aborts the run. Green means "green up
to the first failure" — it does not mean everything after it also passed. When
something fails, fix it and re-run; do not assume the rest of the suite is fine.

## The registry

`run_all_tests.sh` holds one line per entry:

```
<dir relative to Verilog/> :: <make target> :: <required pass pattern>
```

An entry fails when the target exits nonzero, when its output contains a FAIL
line, or when the required pattern is absent. **The pattern must be strict** —
`TB_RESULT: PASS` by convention. A test that can pass silently can fail
silently, which is why a testbench without a machine-checkable verdict cannot
be registered at all.

## Coverage, measured

Run `make catalog` in this directory for the live numbers. As of 08-AUG-2026:

| | count |
|---|---|
| testbench sources in the tree | 182 |
| reached by `make test` | 173 |
| orphaned (exist, never run) | 9 |
| RTL modules (excluding sim/fpga) | 307 |
| modules with a matching testbench | 159 |
| modules with none | 148 |

Those numbers used to be guessed. A count of registry lines is *not* a count of
testbenches run — one entry can run several testbenches (the `iv-%` pattern
rules do exactly this), and a testbench can sit in the tree with nothing
pointing at it. `tb_catalog.py` resolves each registry target through its
Makefile — prerequisites, recipe lines, aggregate targets, pattern rules and
expanded variables — to find what is really executed.

## The orphan gate

`make test-tb-catalog` (registered as the first entry in the suite) fails if a
testbench exists that neither the registry reaches nor `ORPHAN_BASELINE` in
`tb_catalog.py` excuses. Writing a testbench and forgetting to register it is
now a build failure, not a silent loss.

The baseline may only **shrink**. Every entry carries a specific reason. The
nine current ones fall into three groups:

**Known-failing on purpose — reproducers for open faults.** These cannot be
registered while the suite is fail-fast; they would block every later test.
Register each the day it goes green.

- `CPU_CS_RWCS_CYCLE_tb.v` — TRA CS (150017) returns 000000, the fault stopping
  SINTRAN III from booting. `make test-cs-rwcs-cycle`.
- `F595_transparency_tb.v` — the F595 FPGA branch lags transparent-latch
  semantics. The fix was tried and **reverted**: it created a combinational
  loop that kills the board. `make test-f595-transparency`.

**No machine-checkable verdict — cannot be gated as written.**

- `MASEL_cycle_tb.v` — prints findings, no `TB_RESULT`. Documents that iverilog
  cannot reproduce the original posedge-MCLK pattern because the testbench
  drives SC and MCLK on the same `posedge sysclk`.
- `MASEL_iw_capture_tb.v` — no verdict, and currently reports 5 PASS / 2 FAIL
  on capture-correctness. Whether those two failures are real is unestablished.
- `DECODE_DGA_COMM_tb.v` — no make target at all, and prints
  `TB_RESULT: FAIL`. Note `errors=0`: the failure is a stale check-count
  constant (got 240865, expected 219100), so the DUT is not implicated. Find
  out why the count moved before touching the constant.

**Board bring-up harnesses, not unit tests.**

- `basys3_mem_test_tb.v`, `qmtech_mem_test_tb.v` — no Makefile in either
  directory; QMTECH work is paused.
- `sd_fat_test_tb.v` — whole-board wrapper; that directory's six registered
  targets cover the pieces.
- `nd120_tang20k_tb.v` — whole-board Tang simulation, covered in practice by
  the `make test-full` Tang gate.

## Untested modules

`UNTESTED-MODULES.txt` is regenerated by `make catalog`. It is a **backlog, not
a failure** — this project has built testbenches where bugs were found rather
than uniformly, and 148 untested modules mostly means 148 modules that have
never misbehaved. Use it to pick targets when a subsystem starts acting up, not
as a number to drive to zero.

## Adding a testbench

1. Put it in the module's own `sim/` directory — there is no central test tree.
2. Make it print `TB_RESULT: PASS` or `TB_RESULT: FAIL <n> errors`.
3. Add a make target in that `sim/Makefile`.
4. Register it in `run_all_tests.sh` with a strict pass pattern.
5. Run `make test-tb-catalog` to confirm it is reachable.

Step 5 is the one that used to get skipped, nine times.
